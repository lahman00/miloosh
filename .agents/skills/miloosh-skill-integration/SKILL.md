## Entry protocol

1. Read repository `AGENTS.md` and `docs/growth/MILOOSH_GROWTH_OS_2026.md`. Verify the actual production SHA, Guardian protection windows and source availability. Public copy in US English; explain decisions to owner in Hebrew.
2. Consult existing `.agents/skills/miloosh-growth-director/SKILL.md`; for SEO / Search Console use `.agents/skills/miloosh-google-recovery-agent/SKILL.md`; for all intended production changes use `.agents/skills/miloosh-release-guardian/SKILL.md`.
3. For fresh organic growth work, use the **already installed** `~/.agents/skills/growth-skill-router/SKILL.md` and its Miloosh profile. Choose one primary skill + at most one genuinely distinct secondary. Only use skills actually present; an absent user-level skill remains unavailable, not silently downloaded.
4. For public design or accessibility, preserve the already approved About/Design Intelligence design authority and project visual QA. Do not install a second design system.
5. For Miloosh Decision Room, Switching Lab and buyer conversion, use the *read-only synthetic validation contracts* of Funnel Intelligence, Conversion Lab, Buyer Journey QA, Performance/Visual QA and Customer Research/Pricing **only if their local workbench exists and is verified**; their statuses stay NOT_INSTALLED globally. The pilot runtime reads synthetic fixtures only. It does not inspect live customer/analytics data, website URLs or account records.
6. State an exact source, window, denominator, observed/hypothesized distinction, primary user decision, and measurable acceptance or explicit UNKNOWN/NOT_RUN. Never claim traffic, conversions, index coverage or verified buyer success from fixture tests.
7. Publishing, fetching protected business/account data, merging/deploying, changing SEO/indexation, paid spend, outreach and partner account edits require their own authorization and the existing release process. Do not weaken Release Guardian, protected SEO windows, affiliate integrity or event classifiers.
